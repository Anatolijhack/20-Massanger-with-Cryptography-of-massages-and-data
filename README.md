# Messenger (C++ / WebSocket / WebRTC / SQL Server)

Серверная часть мессенджера на C++: личные сообщения, группы и каналы, вложения, история с пагинацией, поиск пользователей, онлайн-статусы, непрочитанные, голосовые и видеозвонки (личные и групповые) и докачка пропущенного после обрыва соединения. REST поверх HTTPS, события в реальном времени по WebSocket, хранение в SQL Server через ODBC.

> В той же базе есть магазин (товары, заказы, корзина, платежи). Этот документ описывает только чат.

## Возможности

| Область | Что есть |
|---|---|
| Сообщения | личные сообщения (до 2000 байт), ответы (`reply_to`), редактирование, удаление |
| Вложения | картинки, документы, аудио и видео из белого списка типов, исходное имя файла, скачивание под правильным именем |
| Голосовые и видео | запись на клиенте (`MediaRecorder`), загрузка тем же `/chat/upload`, длительность и тип вложения в сообщениях, воспроизведение с перемоткой (отдача кусками по `Range`) |
| Группы | создание, добавление и удаление участников, выход, переименование, смена роли, передача владения, удаление |
| Каналы | группа с `kind = channel`: писать могут только владелец и админы |
| Чтение | личная и групповая история (постранично), список диалогов, мои группы, состав группы, поиск пользователей |
| Реальное время | доставка по WebSocket, онлайн-статус и «был в сети», «печатает…», ping/pong |
| Прочтение | счётчики непрочитанных по диалогам и группам (сообщения и пропущенные звонки), общий `unread_total`, галочки «прочитано» в личных чатах, синхронизация между устройствами |
| Личные звонки | аудио и видео 1 на 1: вызов, принять, отклонить, отменить, завершить, занято, таймаут 45 секунд |
| Групповые звонки | до 4 человек в группе, вход и выход в любой момент, выкидывание при удалении из группы |
| История звонков | личные и групповые звонки с длительностью и итогом, события `call_log` и `gcall_log`, последний звонок в списке диалогов, докачка после обрыва, пропущенные в счётчике |
| Надёжность | докачка пропущенного (`/chat/sync`, включая правки и удаления старых сообщений), вытеснение мёртвых соединений |
| Защита | хеширование паролей, токены с ограниченным сроком жизни, блокировка после неудачных входов, шифрование тел сообщений и файлов на сервере (AES-256-GCM), проверка членства, лимиты, проверка вложений, серверный таймаут простоя, чистка осиротевших файлов |

## Технологии

- C++17, Visual Studio (проект `Mesendger for chating by me`)
- ODBC Driver for SQL Server
- [nlohmann/json](https://github.com/nlohmann/json)
- OpenSSL: HTTPS, шифрование данных на сервере (AES-256-GCM) и (по желанию) временные учётные данные для TURN
- WebRTC в браузере для звонков, публичный STUN, свой TURN (coturn) по желанию
- HTTPS и WebSocket на порту `8765` (в разработке самоподписанный сертификат)

## Архитектура

```
Клиент ──HTTPS──► Router ──► ChatController ──┐
   │                                          ├──► ChatRepository / GroupRepository ──► SQL Server
   └──WebSocket──► Session ──► ChatService ───┘            ▲
                      ▲            │                       │
                      │            ├──► ChatHub (живые соединения пользователей)
                      │            ├──► CallManager / GroupCallManager (звонки в памяти)
                      └─ws_post────┴──► пул рабочих потоков (вся работа с БД)

Звонки:  клиент ◄──── звук и видео напрямую (WebRTC, при необходимости через TURN) ────► клиент
         сервер только пересылает служебные события (сигнальный канал)
```

- **Поток сокета не ходит в базу.** Входящее событие передаётся в пул рабочих потоков, а результат возвращается в поток сокета через `ws_post`. Медленный запрос к БД не блокирует соединения.
- **`ChatHub`** хранит `weak_ptr` на сессии по пользователям (до 5 на пользователя) и не продлевает им жизнь.
- **Звонки.** Сервер звук и видео не видит, он хранит состояние звонка и пересылает описания сессий (SDP) и сетевые адреса (ICE) между участниками.
- **Репозитории** возвращают готовый JSON или `std::optional`, работа с ODBC собрана в `DbHelpers.h`.

## База данных

База `ProductDb`. Таблицы чата:

| Таблица | Содержимое |
|---|---|
| `Users` | пользователи (`last_seen_at` для статуса «был в сети») |
| `Sessions` | токены входа |
| `LoginAttempts` | счётчик неудачных входов и время блокировки |
| `Messages` | личные сообщения (`body_enc` с зашифрованным текстом, `attachment_url`, `attachment_name`, `reply_to`, `edited_at`, `deleted_at`, `updated_at`) |
| `ChatGroups` | группы и каналы (`name` уникален, `kind` = `group` или `channel`) |
| `GroupMembers` | участники и роли (`owner`, `admin`, `customer`), `last_read_id` и `last_read_call_id` для счётчика непрочитанных |
| `GroupMessages` | сообщения групп (те же поля, что у `Messages`, включая `body_enc`) |
| `DirectReads` | до какого сообщения и до какого звонка собеседника пользователь прочитал личный чат (`last_read_id`, `last_read_call_id`) |
| `Uploads` | загруженные файлы: имя на диске, исходное имя, тип, размер, кто загрузил, длительность аудио и видео (`duration_ms`) |

| `GroupCalls` | история групповых звонков: группа, кто начал, длительность, пик участников |

Скрипт создания схемы удаляет существующие таблицы. Для живой базы используйте миграцию с проверками `IF COL_LENGTH(...) IS NULL`.

## Запуск

1. Выполните SQL-скрипт схемы.
2. Установите ODBC Driver for SQL Server, строка подключения должна указывать на `ProductDb`.
3. Соберите проект (C++17) и запустите.
4. Папка `uploads/chat` создаётся при первой загрузке, процессу нужно право писать в неё.
5. Для HTTPS нужен сертификат. В curl и Postman для самоподписанного используйте `-k` или отключите проверку сертификата.
6. Для звонков браузер даёт доступ к микрофону и камере только на HTTPS или `localhost`.
7. Ключи шифрования: переменные окружения `CHAT_KEYS` (формат `1:<64 символа hex>`, несколько ключей через запятую) и `CHAT_KEY_ACTIVE` (id ключа, которым шифруются новые записи). Без них сервер запускается, но данные пишутся открытым текстом, и об этом сообщается в консоли. При первом запуске с ключами старые сообщения и файлы шифруются автоматически. Ключ нужно хранить отдельно от сервера и от резервных копий базы: потеряв его, вы теряете все зашифрованные данные.
8. Необязательно: TURN-сервер (coturn). Адрес и секрет задаются переменными окружения `TURN_HOST` и `TURN_SECRET`; без них выдаётся только публичный STUN, этого хватает для звонков на одном компьютере и в одной сети.

## Аутентификация

Токен выдаётся при входе и передаётся:

- в HTTP: заголовок `Authorization: Bearer <token>`
- в WebSocket: первым сообщением `{"type":"auth","token":"<token>"}`

Пароли хранятся только в виде хеша (`<алгоритм>`, с солью). Токены случайные, лежат в таблице `Sessions` и истекают через `<срок>`. После серии неудачных входов логин временно блокируется (таблица `LoginAttempts`). WebSocket-соединение без активности сервер закрывает через `<таймаут>`.

## HTTP API

Все маршруты, кроме отдачи файлов, требуют токен. Имена групп в пути кодируйте (`encodeURIComponent`).

| Метод | Путь | Описание |
|---|---|---|
| POST | `/chat/upload?duration_ms=` | загрузка файла (`multipart/form-data`, поле `file`); `duration_ms` необязателен и принимается для аудио и видео; в ответе `file_url`, `file_name`, `kind`, `duration_ms` |
| GET | `/uploads/chat/:name` | отдача файла: картинки, аудио и видео со своим типом и поддержкой `Range` (ответы 206 и 416), документы как скачивание |
| GET | `/uploads/chat/:name/:filename` | скачивание под исходным именем (имя в ссылке должно совпасть с сохранённым) |
| GET | `/chat/history?with=&before=&limit=` | личная история, от новых к старым (лимит 1–100) |
| GET | `/chat/dialogs` | диалоги и группы с последним сообщением и последним звонком (`last_call`, `last_is_call`), `unread` и `unread_calls` по каждому, `unread_total` в целом |
| GET | `/chat/sync?dm_after=&group_after=&call_after=&gcall_after=&since=` | всё новое после курсоров и всё изменённое после `since`; в ответе `messages`, `group_messages`, `calls`, `group_calls`, `server_time`; нулевой курсор звонков значит «звонки не нужны» |
| GET | `/users/search?q=` | поиск по началу логина среди тех, кому можно писать (от 2 символов, до 20 результатов) |
| GET | `/chat/groups` | мои группы |
| POST | `/chat/groups` | создать группу или канал: `{"name","kind","members":[]}` |
| GET | `/chat/groups/:name/members` | состав группы |
| GET | `/chat/groups/:name/history?before=&limit=` | история группы |
| GET | `/chat/groups/:name/calls?before=&limit=` | история групповых звонков |
| POST | `/chat/groups/members/add` | `{"group","login"}` |
| POST | `/chat/groups/members/remove` | `{"group","login"}` |
| POST | `/chat/groups/leave` | `{"group"}` |
| POST | `/chat/groups/rename` | `{"group","name"}` |
| POST | `/chat/groups/role` | `{"group","login","role":"admin"|"customer"}` |
| POST | `/chat/groups/transfer` | передать владение: `{"group","login"}` |
| POST | `/chat/groups/delete` | `{"group"}` |
| GET | `/chat/calls?with=&before=&after=&limit=` | история личных звонков (`with` необязателен, `after` для докачки пропущенных) |
| GET | `/chat/call/config` | список STUN и TURN серверов для WebRTC (TURN с временными логином и паролем) |

## WebSocket-протокол

### Клиент отправляет

```json
{"type":"auth","token":"..."}
{"type":"message","to":"alice","text":"Привет","attachment":"/uploads/chat/<имя>","reply_to":21}
{"type":"message","group":"Team","text":"Всем привет"}
{"type":"edit","to":"alice","id":21,"text":"Исправлено"}
{"type":"delete","group":"Team","id":21}
{"type":"typing","to":"alice"}
{"type":"read","to":"alice","id":123,"call_id":45}
{"type":"read","group":"Team","id":45,"call_id":7}
{"type":"read","group":"Team","call_id":7}
{"type":"ping"}
```

Правила: указывается либо `to`, либо `group`. Нужен `text` или `attachment`. В `attachment` передаётся только `file_url` из ответа загрузки, а не полная ссылка; прикрепить можно только свой файл.

Звонки:

```json
{"type":"call_invite","to":"alice","video":false}
{"type":"call_accept","call_id":"..."}
{"type":"call_reject","call_id":"..."}
{"type":"call_cancel","call_id":"..."}
{"type":"call_end","call_id":"..."}
{"type":"call_signal","call_id":"...","data":{"sdp":{...}}}

{"type":"gcall_join","group":"Team","video":true}
{"type":"gcall_leave","call_id":"..."}
{"type":"gcall_signal","call_id":"...","to":"alice","data":{"candidate":{...}}}
```

### Сервер присылает

| Тип | Когда |
|---|---|
| `auth_ok` | успешный вход |
| `message`, `group_message` | входящее сообщение; если есть файл: `attachment`, `attachment_name`, `attachment_kind` (`image`, `audio`, `video`, `file`) и для аудио и видео `attachment_duration` в миллисекундах |
| `sent`, `group_sent` | подтверждение отправителю (с `id` и временем) |
| `message_edited`, `message_deleted` | правка или удаление |
| `typing` | собеседник печатает (прятать через ~5 секунд без новых событий) |
| `read` | другим устройствам читающего: чат прочитан до `id` и (или) `call_id`, счётчик сбросить |
| `read_receipt` | собеседнику в личном чате: его сообщения до `id` прочитаны |
| `presence`, `presence_snapshot` | онлайн-статус собеседников и их `last_seen` |
| `pong` | ответ на `ping` |
| `call_ringing`, `call_incoming` | звонящему: вызов пошёл; вызываемому: входящий звонок |
| `call_accepted` | звонящему: можно создавать предложение |
| `call_rejected`, `call_cancelled`, `call_taken`, `call_ended` | отклонён, отменён, принят на другом устройстве, завершён (с `reason`) |
| `call_signal` | служебные данные от второго участника |
| `call_log` | звонок завершён, запись попала в историю |
| `gcall_active` | после входа: где сейчас идут групповые звонки в моих группах |
| `gcall_started`, `gcall_ended` | в группе начался или закончился звонок |
| `gcall_joined` | я вошёл в звонок, в ответе состав участников |
| `gcall_peer_joined`, `gcall_peer_left` | участник вошёл или вышел |
| `gcall_signal` | служебные данные от конкретного участника |
| `gcall_kicked` | меня убрали из звонка (удалён из группы) |
| `gcall_log` | групповой звонок завершён, запись попала в историю |
| ошибка | `unauthorized`, `rate_limited`, `bad_request`, `empty`, `too_long`, `recipient_not_found`, `group_not_found`, `forbidden`, `reply_not_found`, `message_not_found`, `user_offline`, `callee_busy`, `already_in_call`, `call_not_found`, `call_full`, `too_large`, `busy`, `server_error` |

## Звонки

**Личный звонок.** Звонящий отправляет `call_invite`, вызываемому приходит `call_incoming` на все его устройства. После `call_accept` звонящий получает `call_accepted`, создаёт предложение и обменивается с вызываемым описаниями и сетевыми адресами через `call_signal`. Дальше соединение идёт напрямую. Остальные устройства вызываемого получают `call_taken` и перестают звонить.

**Групповой звонок.** Комната привязана к группе, одна комната на группу. Первый вошедший её создаёт, вся группа получает `gcall_started`. Входящий в комнату получает список участников и сам предлагает соединение каждому из них, остальные ждут. Каждый участник соединяется с каждым (до 4 человек). Когда выходит последний, комната удаляется и группа получает `gcall_ended`.

**Правила.**
- Звонить можно тем, кому можно писать (`can_message`), в каналах звонков нет.
- Человек может быть только в одном звонке, личном или групповом.
- Звонок привязан к устройству, на котором его приняли.
- Вызов без ответа сбрасывается через 45 секунд (`missed`).
- Закрытие вкладки завершает звонок этого устройства.
- Удаление из группы выкидывает человека из её звонка, удаление группы закрывает звонок.

**История.** Запись создаётся один раз, когда звонок завершён. Итог: `completed`, `missed`, `rejected` или `cancelled`. Время считает база данных. В истории только метаданные: кто, когда, сколько длилось, без содержания разговора и без сетевых адресов.

**Пропущенные.** В личном чате пропущенным считается звонок со статусом `missed` или `cancelled` для вызываемого. В группе пропущенный звонок это тот, который закончился, пока вы были участником группы, в котором вы не участвовали и который не начинали. Такие звонки входят в `unread` диалога (отдельно `unread_calls`) и в `unread_total`. Отметка прочитанным делается событием `read` с `call_id`: у звонков своя позиция «прочитано до звонка с `id`».

| Пароли | хеш с солью |
| Сообщения и файлы в пути | TLS (HTTPS и WSS) |
| Звук и видео в звонках | шифруются всегда (DTLS-SRTP), через сервер не проходят, ключей у сервера нет |
| Служебные данные звонка (SDP, ICE) | идут через сервер по WSS |
| Тела сообщений и содержимое файлов на сервере | шифруются AES-256-GCM перед записью, ключи из окружения |
| Имена файлов, метаданные чата и звонков, названия групп, логины | хранятся открытыми |
| История звонков | только метаданные (кто, кому, когда, сколько), без содержания |

Это не сквозное шифрование: описание сессии проходит через сервер, поэтому в теории сервер мог бы встать между участниками звонка, а сервер сам расшифровывает сообщения и файлы при выдаче. Шифрование на сервере защищает от утечки копии базы, дампа и папки с файлами, но не от того, кто контролирует работающий сервер и его ключи. Проверка собеседника по коду безопасности и блочное шифрование больших файлов в планах. Дополнительно можно включить шифрование диска (BitLocker) и прозрачное шифрование базы (TDE): они защищают всё остальное и не требуют изменений в коде.

## Проектные решения

- **Аутентификация.** Пароль не хранится, только хеш с солью. Токены со сроком жизни, блокировка перебора паролей по логину, неактивные соединения закрываются сервером, а при закрытии сессия снимается с хаба и собеседники получают статус «не в сети».
- **Звонки через сигнальный канал.** Звук и видео через сервер не идут, поэтому сервер не нагружается медиа и не может его прослушать. Состояние звонков хранится в памяти, потому что оно нужно только пока звонок идёт.
- **Временные учётные данные TURN.** Логин и пароль действуют час и вычисляются из секрета, общего с coturn, поэтому постоянного пароля клиенты не получают.
- **Непрочитанные как позиция, а не флаг.** Хранится «прочитано до `id`» на пару пользователей или участника группы, а не отметка на каждом сообщении. Позиция только растёт, поэтому повторные и запоздавшие отметки безопасны. Свои и удалённые сообщения в счётчик не входят, а новый участник группы не получает счётчик по сообщениям до вступления. Пропущенные звонки считаются тем же способом, со своей позицией.
- **Единый ответ «не найдено».** Несуществующая группа, чужая группа и несуществующий получатель отвечают одинаково, чтобы нельзя было перебирать логины и имена групп.
- **Курсорная пагинация** по `id` вместо `OFFSET`: история не «съезжает» при новых сообщениях, запрос идёт по индексу.
- **Мягкое удаление.** Строка остаётся, текст и вложение стираются. Ответы на удалённое сообщение не ломаются.
- **Докачка двумя курсорами.** Новые сообщения по `id`, правки и удаления по `updated_at`. Время курсора выдаёт сервер из БД (минус запас в 5 секунд), поэтому расхождение часов клиента не важно. Повторы безопасны, клиент применяет сообщения по `id`.
- **Права берутся только из сессии.** Владелец группы, отправитель сообщения и участник звонка никогда не приходят из тела запроса.
- **Вложения.** Белый список типов, имя файла на диске генерирует сервер (защита от path traversal), исходное имя хранится в базе и очищается от путей и запрещённых символов, расширение ставится по реальному типу. В `attachment` принимается только свой файл. Не-картинки отдаются как скачивание, чтобы браузер не выполнял их.
- **Шифрование данных на сервере.** Тела сообщений и содержимое файлов шифруются AES-256-GCM перед записью. В каждой записи лежат версия формата, идентификатор ключа и случайный nonce, поэтому ключи можно менять без остановки: новое пишется активным ключом, старое читается своим. Контекст (отправитель и получатель или группа, имя файла) входит в проверяемые данные, поэтому зашифрованное тело нельзя незаметно перенести в другую строку или чат. Шифрование живёт только в слое хранения (репозитории и отдача файлов), остальной код работает с обычным текстом. Ключи берутся из окружения, а не из кода и базы. Зашифрованные файлы лежат в отдельной папке `uploads_enc/chat`, старые переносятся при запуске. Ошибка шифрования отклоняет запись: открытым текстом ничего не пишется.
- **Аудио и видео.** Клиент записывает через `MediaRecorder` и загружает как обычное вложение. Тип проверяется и по названию, и по началу файла (webm, ogg, mp4, mp3). У каждого формата своё расширение, поэтому сервер при отдаче определяет тип без разбора файла. Файлы отдаются кусками по `Range` (до 4 МБ за ответ): работает перемотка, а видео не читается в память целиком. Длительность присылает клиент (в записях `MediaRecorder` из Chrome её нет в самом файле), сервер проверяет только разумный диапазон, она нужна лишь для отображения.
- **Параметризованные запросы** везде, спецсимволы `LIKE` экранируются.
- **Транзакции.** Создание группы, участников, передача владения и запись группового звонка с заходами выполняются атомарно с откатом.
- **Лимиты.** Частота сообщений, загрузок, создания групп, приглашений на звонок, служебных данных звонка и «печатает», размер группы, число соединений на пользователя.
- **Чистка.** Раз в час удаляются файлы старше 24 часов, на которые нет ссылок в БД, вместе с записью об их имени.

## Реконнект на клиенте

1. Экспоненциальная задержка 1, 2, 4 ... до 30 секунд.
2. После переподключения заново `auth`.
3. Затем `GET /chat/sync` с последними `id` (отдельно для личных и групповых) и сохранённым `server_time` как `since`.
4. Звонки докачиваются тем же запросом: курсоры `call_after` и `gcall_after` (последние известные `id` личных и групповых звонков). При первом запуске начальные значения берутся из `last_call.id` в `/chat/dialogs`.
5. Heartbeat: `ping` каждые 25 секунд, нет входящих 60 секунд значит закрыть и переподключиться.

## Проверка

Ручной сценарий: файлы, личные сообщения, группа и канал, управление и передача владения, правки и ответы, чтение, онлайн и typing, непрочитанные, звонки (два пользователя в двух вкладках), реконнект с докачкой, чистка файлов. Нужны три пользователя (владелец, участник, посторонний), три вкладки WebSocket и curl или Postman. Звонки проверяются только в браузере. После прогона в консоли сервера не должно быть `ODBC Error` и `HANDLER EXCEPTION`. Служебную часть звонков (вызов, принятие, отказ, таймаут, занято, история, счётчики) можно проверить в Postman и curl; сам звук и видео проверяются только в браузере. Отдача аудио и видео проверяется запросами с заголовком `Range` (ответы 206 и 416) и воспроизведением в браузере. Шифрование, сообщения и вложения проверяются вручную по `TESTING.md` (Postman и несколько запросов к базе). Автоматических тестов и CI пока нет.
